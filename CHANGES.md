# CHANGES

## 1.3.0

- `RevitServerApi.EncodePath` percent-encodes every folder/model name (segment between `|`) with `Uri.EscapeDataString`; the `|` separator stays as is. Separator normalisation is unchanged (`\` and `/` -> `|`, `||` collapsed, leading `|` added; `null`, `""` and `"|"` still give `"|"`).
  - Fixed: names containing `#`, `?` or an existing `%XX` sequence. Before, the request was cut off at `#` (the rest became a URL fragment and was not sent), `?` turned the rest of the command into a query string, and `%XX` (for example a literal `%23` in a name) was decoded by the server into another character.
  - All other reserved characters (`&`, `+`, `;`, `=`, `(`, `)`, `,`, `'`, `!`, `*`, `$`, `:`, `@`, `[`, `]`) are now escaped explicitly too; before they were sent as is. For example, parentheses now go as `%28`/`%29`. On net48 `!`, `'`, `(`, `)` and `*` are escaped only when the host process targets .NET Framework 4.5 or later; in a legacy host (for example Windows PowerShell 5.1) `Uri.EscapeDataString` leaves them as is.
  - Spaces and non-ASCII characters were already percent-encoded by `System.Uri` in 1.2.1; they go over the wire exactly as before.
  - Names made only of `A-Z a-z 0-9 - _ . ~` are encoded exactly as before.
  - How a real Revit Server handles the newly escaped characters has not been verified yet (checked only against a local HTTP stub).
  - All extension methods build commands through `EncodePath`, so callers keep passing raw names. Code that escaped names itself before calling `EncodePath` must stop doing so, otherwise they are escaped twice.
- `FolderExtensions.RenameFolderAsync`: the new name is escaped in the `newObjectName` query parameter.
- `FolderExtensions.GetAllModelsRecursiveAsync` throws `RevitServerApiException` ("Empty response for folder contents: {folderPath}") when a folder's `contents` response has an empty body. Before, such a folder was skipped silently and the method returned an incomplete list of models without any error.
- `RevitServerApiException` and `RevitServerUiApiException`: new properties `StatusCode` (`HttpStatusCode?`) and `ResponseContent` (`string`), filled when the server returned an HTTP error response (for example `404 NotFound` for a missing model); both are `null` when no HTTP response was received. New constructor `(string message, HttpStatusCode statusCode, string responseContent, Exception innerException)`; existing constructors and message texts are unchanged.
- Direct export (`ModelExporter.ExportAsync`, `ExportExtensions.ExportModelAsync`, `FolderExtensions.CreateLocalModelWithoutToolAsync`) no longer uses Autodesk `RS.Enterprise.Common.ClientServer.Proxy.dll`. It opens its own WCF channel to `net.tcp://{ServerHost}/ModelService{RevitVersion}/ModelService.svc/tcpstream` (`NetTcpBinding` without security, streamed, 5 GB per file, reader quotas of Autodesk's streamed binding; timeouts: open 1 min, close 1 min, send 10 min, receive 10 min). The year is only a part of the address, so any server year that exposes `/ModelService{year}/` can be used with the same client assemblies. Verified live on Revit Server 2022, 2023, 2024 and 2025 (a docker test stand; net48 and net8.0), all with the same test models saved in Revit 2022 format (copied unchanged onto the 2023-2025 servers); with `CreateLocal`, `BasicFileInfo` matched the output of the official RevitServerTool 2022 and 2024. Not tested: models saved by Revit 2023 or later, and Revit Server 2021 and earlier. Revit Server 2026 and 2027 are expected to work through the same endpoint pattern but have not been verified against a live server.
  - All calls go over the streamed channel on every target. Before, net6.0/net8.0 fell back to the buffered endpoint for downloads (Autodesk's streamed binding sets `PortSharingEnabled`, which does not exist on .NET Core).
  - Call order as in RevitServerTool `createLocalRVT`: `IdentifyModel`, `LockData`, `GetListOfModelDataFilesWithoutLocking`, `DownloadFile` per file, `ModelDataFormatVersion` (asked while the lock is held; RevitServerTool asks after unlocking), `UnlockData`. The data format version reported by the server is used to assemble the RVT (before: always `DataFormatVersion.Latest`; on the tested Revit Server 2022-2025 servers, with 2022-format models, the server reported `HaveProjectInformationStream`, the same value as `Latest`).
  - `LockData` statuses other than `Locked`/`WasLocked` and `GetListOfModelDataFilesWithoutLocking` statuses other than `Success` (or an empty list) are errors that name the status. Before, the statuses were not checked. `LockData` `Busy` and the lock contention faults (`DataLockContentionFault`, `PermissionLockContentionFault`) are retried like RevitServerTool does: up to 5 attempts, 10 s apart, cancellable; the error after the last attempt names the number of attempts.
  - `UnlockData` is always called once the read lock may have been taken, also after an error or cancellation. Before, it was never called and the read lock stayed on the server until it expired (12 h). It is retried up to 5 times, 10 s apart, when it fails with a communication error (as RevitServerTool does; a timeout is not retried). After cancellation, each attempt waits for the reply for up to 1 min instead of the 10 min send timeout. If `LockData` was interrupted (cancelled or timed out) and the first `UnlockData` finds no lock, `UnlockData` is sent once more after 5 s, because the server may still apply the interrupted `LockData`; a lock applied even later stays until it expires (12 h) or until the next export of this model from this machine releases it. If only `UnlockData` fails, the RVT file is still written and the export throws `InvalidOperationException` saying so, with the file path in `Data["RevitServerNet.ExportedFile"]` (this key means the file is complete and only the lock release failed); if the export fails for another reason, the `UnlockData` failure is added to that exception's `Data["RevitServerNet.UnlockDataError"]`.
  - Exports of the same model hold a named mutex from `LockData` to `UnlockData`, named like RevitServerTool's (`{user}_{model path}_{server}`): the server keeps one read lock per user name (`RevitServerTool:{machine}:1`, unchanged), so overlapping exports in the same Windows session would release each other's lock. The name is case-sensitive and uses `ServerHost` and the model path as given, so the same model spelled differently is not serialized; a name longer than 260 characters is replaced by a hash (and then does not coordinate with RevitServerTool). RevitServerTool waits on the same mutex only when it uses the same user name: its number (`RevitServerTool:{machine}:{n}`) is assigned per installation folder, so another installation on the same machine (for example RevitServerTool 2024 next to 2022) uses `:2` or higher and holds its own read lock. When `UnlockData` finds that the confirmed read lock was already released (another export under the same user name released it, or it expired), the export still succeeds and reports it with `Trace.TraceWarning`, or in `Data["RevitServerNet.ReadLockLost"]` of the exception when the export failed.
  - The model data is downloaded and the RVT file assembled in `%TEMP%\RevitServerNet_{guid}`, so `%TEMP%` must hold the model data and the RVT file together (about twice the model size; before, only the data went to `%TEMP%` and the RVT was written directly to `DestinationFile`). The RVT file is then moved under a temporary `.partial` name into the destination folder and renamed to `DestinationFile`: the previous destination file is replaced only after the new file is complete in the destination folder. The temp folder is deleted at the end of the export (a failure to delete it is added to `Data["RevitServerNet.TempCleanupError"]` of the export's exception, or traced with `Trace.TraceWarning` after a success), and later exports delete such folders (also the `RevitServerNet_ModelData_{guid}` folders of earlier versions) once they are more than 7 days old, as RevitServerTool does with its own.
  - A failed download (for example a full disk) aborts the connection before the partly read reply is closed, so the download's own exception is thrown at once (closing a partly read streamed reply makes WCF read the rest of it for up to 1 min, and its error would replace the original one). An error of the close is added to `Data["RevitServerNet.DownloadCloseError"]`.
  - The `CancellationToken` of `ModelExporter.ExportAsync` is honoured (before, it was ignored): checked before the export starts, between the steps and between 80 KB blocks of every download; a waiting call is interrupted by aborting the channel, and waiting for the model's mutex or for a `LockData` retry is interrupted too. The read lock is still released and `OperationCanceledException` is thrown.
  - Errors are exceptions with the operation, model and endpoint in the message (`InvalidOperationException` with the WCF exception as `InnerException`). The `%TEMP%\RevitServerNet_*.txt` diagnostic files are no longer written, and the dead fallback code around the Autodesk proxy is removed.
  - The export runs on a thread-pool thread (`Task.Run`), and `bytesProgress.Report` is called synchronously from that thread after every 80 KB block, with the bytes downloaded so far of the current file. Before, the synchronous WCF calls blocked the calling thread, and when the caller awaited on a UI thread, `Report` ran on that thread. A custom `IProgress<long>` that updates UI controls directly must now marshal to the UI thread itself, or use `System.Progress<T>` created on the UI thread. An exception thrown by `Report` ends the export (the read lock is still released).
- New option `ModelExporterOptions.CreateLocal` (default `false`, the file keeps the server's `BasicFileInfo` as before). When `true`, `BasicFileInfo` is rewritten like RevitServerTool `createLocalRVT` does, through the Autodesk Helper (`ModelBasicFileInfoStream`): worksharing state "Created Local", central path `RSN://{ServerHost}/{model path}`, the server model as central, a new model identity. Checked against RevitServerTool 2022 (on Revit Server 2022) and RevitServerTool 2024 (on Revit Server 2024) output: byte-identical except for the random model identity. A `BasicFileInfo` stream version newer than the loaded Helper supports throws `NotSupportedException`.
- New overloads with `createLocal` and `CancellationToken`: `ExportExtensions.ExportModelAsync(api, modelPath, destinationFile, bool createLocal, string assembliesPath = null, bool overwrite = false, IProgress<long> bytesProgress = null, CancellationToken cancellationToken = default)` and `FolderExtensions.CreateLocalModelWithoutToolAsync(api, modelPipePath, destinationFile, bool createLocal, string revitVersion = null, string assembliesPath = null, bool overwrite = false, IProgress<long> bytesProgress = null, CancellationToken cancellationToken = default)`. Existing signatures are unchanged.
- `ExportExtensions.ExportModelAsync` takes the host from `BaseUrl` without the HTTP port (`new Uri(BaseUrl).Host`, as `CreateLocalModelWithoutToolAsync` already did). Before, a client created with `host:port` sent the HTTP port into the net.tcp address.
- `RevitVersion` must be a four-digit year (`ArgumentException` otherwise); `ServerHost` must be a host name or IP address with an optional port.
- One bundled set of Autodesk client assemblies instead of `RSAssemblies\2019` ... `RSAssemblies\2026`: the Revit 2024 set, unmodified, flat in `RSAssemblies\` (`RS.Enterprise.Common.ClientServer.DataContract`, `.ServiceContract.Model`, `.Helper`, `Autodesk.RevitServer.Social`, `Castle.Core`, `Castle.Windsor`). `Proxy.dll` and `ServiceContract.Local.dll` are no longer shipped. The bundled assemblies are AnyCPU, so a 64-bit process is no longer required for them (other sets, such as the Revit 2025 and 2026 ones, are x64-only).
  - `buildTransitive/RevitServerNet.props` copies them to `<output>\RSAssemblies\` and now also to the `dotnet publish` output; with `PublishSingleFile` they stay files in `<publish>\RSAssemblies\` next to the executable (they are excluded from the bundle). The copy still runs in the MSBuild target `RevitServerNet_CopyRSAssembliesForConsumers` (now through `None` items), so an empty target with that name in the consuming project still turns it off.
  - Loader: search order `AssembliesPath` (if it exists), `<AppContext.BaseDirectory>\RSAssemblies`, `<folder of RevitServerNet.dll>\RSAssemblies`, `<folder of the process executable>\RSAssemblies` (.NET 6 and later, for single-file apps that extract their content), `<Program Files>\Autodesk\Revit {year}\RevitServerToolCommand`; a directory is used only if it directly contains the six files (no recursive search). A directory that does not qualify, an existing `AssembliesPath` too, is skipped (at 1.2.1 an existing `AssembliesPath` was always used, and a set without the required files failed); the skipped directories and the reasons are traced with `Trace.TraceWarning` when a later one is used, and added to loading error messages. On .NET Framework an assembly cannot be loaded from a path longer than 259 characters, also in a long-path-aware process: a directory with such a file is skipped with that reason, and the next directory in the order is used. Before, a year without a bundled folder silently loaded `RSAssemblies\2019`. If nothing qualifies, `InvalidOperationException` lists the searched paths.
  - The assemblies are loaded once per process with one `AssemblyResolve` handler. The first set found without an existing `AssembliesPath` is used for all later exports without one, whatever their year. An export that resolves to another directory in the same process throws `InvalidOperationException`, and loading throws the same exception when an assembly with one of these names is already loaded in the process from another location (for example inside Revit.exe, whose install folder ships `RS.Enterprise.Common.ClientServer.*.dll`); 1.2.1 called `Assembly.LoadFrom` without this check.
  - The Autodesk Windsor container is created when the assemblies are bound, before any server call: a process that binds `Castle.Core` to a version other than 3.2.0.0 (a `Castle.Core` 4.x/5.x dependency on .NET, or a `bindingRedirect` on .NET Framework) fails there with `InvalidOperationException` that names the loaded Castle assemblies, instead of failing after the whole download when the RVT is assembled.
- Added test project `RevitServerNet.Tests` (xUnit, net8.0 and net48): path encoding and wire-level requests against a local HTTP stub; direct export endpoint, version and host checks, loader search order and binding, cancellation before start, the export path up to a refused connection; the export flow with a fake server session (lock lifecycle, retries, error reporting, destination and temp folder handling, the model mutex); export tests against a live Revit Server when `RSN_TEST_RS_HOST`, `RSN_TEST_RS_YEAR` and `RSN_TEST_RS_MODEL` are set (optional `RSN_TEST_RS_REST_HOST`; the live tests of both target frameworks run one at a time, also across test processes). `scripts/package-smoke.ps1` packs the library and checks that a package consumer gets the six assemblies on build, publish and single-file publish.

## 1.2.1

- Direct export (RS Enterprise API, WCF): the client binding is configured for large models.
  - `NetTcpBinding`: `MaxReceivedMessageSize` 5 GB, `MaxBufferSize` `int.MaxValue`, reader quotas raised; for `CustomBinding` the same limits are applied to the transport and message encoding elements.
  - If the channel is already open, the proxy is recreated with a new `NetTcpBinding`: Buffered (`int.MaxValue` limits) or Streamed (5 GB) depending on the endpoint path, with 10/30-minute timeouts.
  - Binding diagnostics are appended to `%TEMP%\RevitServerNet_Binding_Diagnostics.txt`, binding configuration errors to `%TEMP%\RevitServerNet_BindingConfig_Error.txt`.

## 1.2.0

- Added `net6.0` target (`net48;net6.0;net8.0`).
- Direct export (`ModelExporter.ExportAsync`, `ExportExtensions.ExportModelAsync`, `FolderExtensions.CreateLocalModelWithoutToolAsync`) is available on net6.0/net8.0 too, not only on net48; on these targets the package depends on `System.ServiceModel.Primitives` and `System.ServiceModel.NetTcp` 4.9.0.
- `RsModelExporter`: file download falls back to the buffered proxy when the streamed proxy cannot be created (the failure is appended to `%TEMP%\RevitServerNet_StreamProxy_Fallback.txt`); WCF faults from the lock-data call are recognised by type name (`FaultException`, `FaultException<T>`) instead of a `catch` on `System.ServiceModel.FaultException`; downloaded file content is also read from `byte[]` payloads; unused ProxyProvider/"Exact" helper methods removed.
- README: direct export requirements updated for net48/net6/net8.
